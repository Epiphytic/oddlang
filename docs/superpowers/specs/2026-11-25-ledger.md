# Oddlang ledger prototype

Can a single ontology describe an account, an executable transfer, and the effects of a schema change precisely enough for independent consumers to agree? The prototype answers this with one ledger across two versions.

## Source and build contract

A local Turtle domain model owns stable IRIs for Account, its fields, and TransferFunds. Target overlays reference those IRIs and supply names and representation choices. A closed, documented input vocabulary defines what the compiler understands. SHACL checks required declarations. A typed intermediate representation retains each declaration's IRI for errors and change detection. The executable meaning of each supported operation comes from the language specification. Unknown executable constructs and unrepresentable ranges are build errors.

With dependencies installed, builds run offline. Imports resolve from pinned local inputs. Changing triple order or namespace prefixes preserves emitted bytes. Semantic ordering, such as guard priority, must be explicit in the graph.

## Three demonstrations

1. Generate a checked Rust Account type and PostgreSQL table. Both require an ID, an owner and a balance in 0..=9223372036854775807. Exercise their real input boundaries.
2. Interpret and compile a state transition. Read both balances from the starting state, check distinct account identities, a positive amount, sufficient funds and room for the credit. Publish both updates together on success. Every error preserves the entire prior state. Atomicity here concerns a single in-memory operation. Concurrent database transactions would need separate semantics.
3. Save a v1 account event and a populated database row. Keep the owner field IRI while renaming its physical column. Add required currencyCode to v2 with an explicit CAD reader default justified by a CAD-only v1 ledger. Demonstrate a failing compatibility check without that default, a successful old-event read with it, and a migration preserving the original owner and balance.

The first executable target is Rust. PostgreSQL and Avro exercise storage and wire representations. A second executable target, a surface syntax and LLM-assisted authoring can each be evaluated after these demonstrations.
