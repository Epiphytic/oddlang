# Oddlang ledger prototype

Can one ontology describe an account, an executable transfer and the effects of a schema change precisely enough to generate working Rust, PostgreSQL and Avro artifacts? A ledger spanning two versions supplies three experiments. The Rust interpreter and Rust source generator share a loader. An independent executable ledger oracle checks their interpretation of the source fixture.

## 1. Compile the account and query its dependencies

A pinned local Turtle import graph defines Account, its fields and TransferFunds using stable IRIs. Target overlays refer to those IRIs and supply representation choices. The Rust typed loader validates the closed vocabulary, cardinalities, references and target ranges. Defer SHACL until there is a second consumer of structural constraints. Fetch locked Cargo dependencies once and run the build offline.

Require IRIs on entities, fields, operations, guards, errors and target projections. Anonymous expression and assignment nodes may carry structure. Diagnose a malformed anonymous subtree by its nearest named owner and operand path. Reject cyclic expressions, unknown executable terms and ambiguous operands. Triple order, prefix spelling and blank-node labels have no observable effect on generated bytes or diagnostics.

The v1 Account has a unique text ID, a required text owner and a balance in 0..=9223372036854775807. The generated Rust balance constructor accepts i128 and checks before narrowing. PostgreSQL enforces the same range with BIGINT, NOT NULL and a nonnegative check.

Run a reverse dependency query over the root's transitive import closure. Starting at the balance IRI, return the named transfer and each affected Rust, SQL and event projection, including indirect dependencies. Adding a separately imported projection must change the result without changing compiler code. Compare this workload with a stable-ID TOML fixture using the same edges. Record author edits, duplicated relationships and maintenance of traversal code. Retain Turtle if it removes duplicate dependency declarations or bespoke traversal logic for this workload. If neither advantage materializes, prefer TOML for the next iteration. A successful query alone only establishes feasibility.

## 2. Execute TransferFunds

State is a map from unique case-sensitive string IDs to checked Account records with matching IDs. Arguments are source ID, destination ID and signed i64 amount in the ledger's smallest unit. Every i64 is a representable input. The operation applies to the v1 single-currency ledger.

| Priority | Guard must hold | Error local name |
| --- | --- | --- |
| 1 | Source exists | SourceMissing |
| 2 | Destination exists | DestinationMissing |
| 3 | IDs differ | SameAccount |
| 4 | Amount > 0 | NonPositiveAmount |
| 5 | Source balance ≥ amount | InsufficientFunds |
| 6 | Destination balance + amount ≤ 9223372036854775807 | DestinationOverflow |

Error names expand under the fixed namespace `urn:oddlang:ledger:error:`. Return the first failing guard's error IRI and preserve the entire state. Priorities are explicit unique positive integers within an operation. Evaluate guards in ascending order and stop immediately on failure. Evaluate all reads against the entry snapshot. Widen integer operands to signed i128 before arithmetic. Reject graphs whose declared operand intervals could exceed i128. After guards pass, debit the source and credit the destination simultaneously. Check all results before publishing. Reject duplicate assignment targets and require distinct resolved targets before commit. All other records and fields survive. Atomicity covers one in-memory call.

A separate normative vocabulary and evaluation document precedes either executor. Both executors implement graph primitives. The test oracle implements the table above directly from plain fixture inputs and uses no production parser, model, evaluation or generated code. Conformance also requires that changing a supported expression in the graph changes both executors' answers as predicted.

## 3. Evolve the account and its event

The v1-to-v2 transition records that all historical v1 balances were CAD. Keep the owner IRI and rename SQL column owner to owner_name and Avro field owner to ownerName. The v2 reader carries owner as a field alias. Add required text currencyCode (SQL currency_code). In one transaction rename the column, add the new column, backfill CAD and set NOT NULL. Leave no SQL default. New accounts must specify a currency. Compare the resulting catalog with fresh v2 DDL.

Generate the v2 Avro reader's CAD default from the transition. It applies whenever that reader encounters a compatible writer schema lacking currencyCode, including future such schemas. Preserving v1 readability requires keeping an equivalent default in later readers. V2 writers supply the field. Binary resolution yields field values which must pass the generated Account constructor, including its balance check. The compatibility verdict concerns v1 writer → v2 reader and the supported record, string and long subset. It comes from the IRI-keyed model diff plus Avro name, alias, type and default rules. A real binary decode independently confirms the verdict. Avro implementations may optionally support aliases, so the Rust resolver must demonstrate field-alias support. [Apache Avro specification](https://avro.apache.org/docs/1.12.0/specification/#aliases)

The end-to-end witness is a generated Rust Account persisted to PostgreSQL, read back into Rust, serialized with the generated writer schema and resolved into a checked reader Account. Compare every field with the expected versioned value. A second executable target, surface syntax and LLM-assisted authoring remain future experiments.
