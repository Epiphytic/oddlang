# Portable HTTP conformance design

Oddlang publishes versioned contracts and deterministic conformance obligations. Each app claims the stable feature IRIs and roles it implements. Rust providers and TypeScript consumers are the first generated targets. A Go consumer exercises the same release using its own tools. Local application code owns behavior, persistence and presentation.

## Contracts and coverage

Use a closed HTTP vocabulary with named declarations for operations, records, fields, bounds, errors and observable postconditions. Name each supported constraint and give it a role-specific rule. A compiler must reject unknown normative declarations. Keep metadata and advisory target hints outside the rule inventory. The `http.provider` role checks parsing, responses and state transitions. The `http.consumer` role checks request encoding, response decoding and named error handling. The first implementation reports evidence only for those roles. Existing storage and migration evidence retains its ledger scope.

The obligation key is (release identity, version, manifest SHA-256, rule-set version, declaration IRI, role, rule ID). Feature claims name operation IRIs. Walk operation dependencies and apply rules to the request or response position where each declaration is used. A case can witness multiple obligations. Each association records the specific position and kind of outcome it exercised. Compute the inventory from the validated graph independently of the emitted target code and selected cases. Each case names the obligations it exercises. Static rules produce deterministic positive and negative witnesses from the written rules. Behavior needing context uses a portable scenario specifying inputs, fixture state and expected observations or a separately tested oracle. A missing witness is a release-blocking gap for its declared role. A failed or unexecuted required case fails an implementation's conformance check. A claim is a nonempty set of feature-IRI/role pairs and includes the transitive obligations each feature needs. Evidence names the exact release pin, rule set and claimed pairs.

A protocol binding defines the actions and observations for its cases. HTTP provider cases send requests to a real listener. HTTP consumer cases run native client code against a scripted peer that records the request and serves valid and invalid replies. Use per-case isolation and bounded execution. Normalize JSON for comparison after strict parsing. Require exact string values, HTTP methods, decoded path values, status and media type. Ignore object member order, whitespace and transport headers outside the contract. Raw bytes are preserved in portable cases so runners can exercise invalid UTF-8 and malformed JSON. Wire vectors and evidence have a versioned JSON format and native test runners. A shared runtime is unnecessary.

## First HTTP profile

Start with UTF-8 JSON requests and responses, required record fields, text, booleans and decimal-string signed or bounded i64. Next add nested records, lists, explicit optional/nullable fields and closed tagged unions. Validate decimal lexemes and range before native conversion. For i64 use `0` or an optional minus followed by a nonzero leading digit and decimal digits. Reject `-0`, leading zeros, signs other than minus, exponent notation, whitespace inside the string and JSON number tokens. IDs use exact Unicode scalar sequences with no normalization. For request and response objects reject duplicate and unknown members. Optional means a field can be absent. Nullable means a present value may be JSON null.

The demo publishes a new HTTP contract identity. It imports the immutable v1 ledger semantics for transfer. Existing ledger v2 stays a separate structural release. The profile uses `GET /accounts/{id}` to observe balances and `POST /transfers` to execute transfers. The first HTTP release returns the Account fields `id`, `owner` and decimal-string `balance`. Transfer uses `source`, `destination` and decimal-string `amount` and returns the two updated accounts as `source` and `destination`. Lookup success and transfer success use HTTP 200. Errors are JSON objects with a single `error` field containing the error IRI. Map missing accounts to 404, same account and nonpositive amount to 422, and insufficient funds and destination overflow to 409. Malformed JSON or a value outside its request schema is a distinct 400 contract error. Unsupported request media type is a distinct 415 contract error. HTTP-only errors are `urn:oddlang:http:error:InvalidRequest` (400), `urn:oddlang:http:error:AccountMissing` (lookup 404) and `urn:oddlang:http:error:UnsupportedMediaType` (415). Match routes on raw slash-separated path segments. Percent-decode the bound ID once and reject invalid percent escapes, invalid UTF-8, and IDs equal to the empty string, `.` or `..`. Clients reject those IDs before issuing a request. In paths, `+` is literal. Validate path, then request media type for the POST, then body, then domain guards. Distinguish transport failures from declared responses. Use strict UTF-8 and reject a byte order mark, unpaired Unicode surrogates, empty bodies, trailing non-whitespace, and duplicate member names after decoding escapes. Require `application/json` for POST bodies, matched case-insensitively, with no parameters or just a UTF-8 charset parameter. Treat a missing Content-Type as unsupported. Phase 1 specifies the limits of declared routes and responses, including which framework failures are outside the supported profile. Ledger guard order and atomicity come from the ledger core spec. For this exact transfer, distinct account IDs and complementary bound guards make the two commit-time built-in errors unreachable. If a changed operation can reach either error, publication requires an explicit HTTP mapping and case.

Publish a self-contained OpenAPI 3.1.0 projection and JSON Schema 2020-12 per release. Describe decimal strings structurally and record exact range metadata with an Oddlang extension. The native codecs and conformance cases enforce that range. Support local references only in generated documents. [OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0) · [JSON Schema 2020-12](https://json-schema.org/draft/2020-12)

## Native implementation and evolution

A project overlay selects required bindings by role and target. Its advisory library hints can guide developers and LLMs. Validate that a required binding is available. Hints affect adapter authoring and can be captured with reviewed source in a target lock. They cannot change expected results, selected obligations, or release identity.

Generate checked Rust boundary types and an HTTP binding backed by a native service. Generate one browser-safe TypeScript client and runtime codec package. Exercise it through both Node server-side rendering and React in a browser. The Rust demo owns ledger state and Node and React own presentation. Go takes the portable bundle and publishes the same evidence format using standard-library tests. Runners and version-skew fixtures run offline after toolchain setup.

A workspace pins the same contract for each of its targets. An external consumer owns its own pin. Verify import closure and payload bytes offline. Model a deliberate second HTTP release that renames the required wire field `balance` to `balanceMinor` under the same stable field IRI. Exercise the expanded JSON vocabulary in a separate fixture contract. Treat cross-version pairs as incompatible in both directions and demonstrate separate deployment base URLs. A mismatched transfer can still commit before its client fails to decode the response. Keep native field names stable across this wire rename. Promote a workspace pin only with its rebuilt targets and fresh evidence. The fixture exercises a breaking rollout without production deployment orchestration.

The first release covers this finite HTTP profile and its mixed-stack examples. Additional protocols can reuse the obligation model with their own bindings. Authentication, streaming, arbitrary constraints, production rollout automation, browser cross-origin policy and database-backed HTTP service support can be scoped as follow-up work.
