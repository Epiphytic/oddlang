# Generated foreground relay activation

The generated daemon needs to admit one explicitly selected relay, open retained stores under its profile lease, authenticate and publish its current key package through the normal foreground startup path. The companion declares the relay route and publication policy and binds the native libraries. The original binary and its source stay outside the candidate build.

- [x] Project an opt-in foreground relay runtime. In an unrelated fixture, verify that the graph and native binding must agree, the emitted route has bounded WebSocket frames and private bootstrap directories, and existing loopback TLS projections retain their exact output.
- [ ] Bind the companion daemon's ordinary foreground handler to that projection. On the test-owned relay, confirm stable signed publication, authenticated relay acceptance, account transport activation, a separately named provider-ready phase and owned cleanup. Stop reporting readiness after transport or forwarding loss. Use freshly provisioned file identities and no external executable inside the generated owner.

A provider-ready phase describes the authenticated transport boundary. Command admission, worker execution, and completion are separate qualifications.

On transport loss, the owner attempts in-band deactivation only while a connection remains available. The foreground scope still closes the native client, forwarder and retained stores and releases the owned status socket.
