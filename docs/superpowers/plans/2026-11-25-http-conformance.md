# Portable HTTP Conformance Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development or superpowers:executing-plans to implement the phases in order. Steps use checkboxes for tracking.

**Goal:** Ship one contract-driven Rust HTTP provider with deterministic conformance for native Rust, TypeScript and independent Go implementations.

**Architecture:** A Rust compiler resolves pinned Turtle contracts and publishes an obligation inventory, portable cases and schema projections. Protocol bindings turn cases into provider interactions and consumer peer tests. The same browser-safe TypeScript package serves Node SSR and React.

**Tech stack:** Rust, Oxigraph, Serde, SHA-256, Axum, TypeScript, Node.js, React, Go and a headless browser.

**Spec:** [Portable HTTP conformance](../specs/2026-11-25-http-conformance.md) and [ledger core](../../language/ledger-core.md).

## Implementation rules

- Keep the existing ledger CLI and offline releases working. Add HTTP commands under `oddlang http`. Use `Cargo.lock` and lockfiles for native examples and pin the browser binary in the setup script. Begin with the existing TypeScript 5.9.3 baseline. Pin exact Node, Go, Rust and browser versions in phase 1 and verify them in the setup script.
- Keep the legacy ledger pins and manifests readable. Start the independent, explicit conformance rule-set version at `1`. Assign a new rule-set version only to releases using changed rules. Pin the chosen version in the authoring input and keep the earlier derivation path for reproducing prior releases. Keep derived payloads deterministic under equivalent Turtle. Source bytes and the manifest that pins them retain their exact-byte identity. Diff sorted declaration IRIs and versioned artifacts.
- Start each phase with failing tests, implement the named entry points, run its targeted check and commit with graph status and evidence. Ask Claude CLI in auto permission mode to review each phase at its verified commit before marking the phase done. Address findings with fresh checks. Save concise findings and dispositions in the work ontology. Independent tasks within a phase may use subagents after their shared interfaces are written.
- Use one setup command (`scripts/setup-http-conformance.sh`) to provision pinned dependencies and one offline command (`scripts/verify-http-conformance.sh`) to run the final matrix. Missing prerequisites fail with the missing tool or pin named.

## Review focus

- Make a release fail when one known normative declaration has no witness and when an unknown predicate appears in its place.
- Test consumer output against a scripted peer. Deliberately mutate its amount encoder and its response validator in separate runs.
- Exercise the first failing ledger guard, with two failing guards in the same fixture and post-state read over HTTP.
- Check malformed JSON, duplicate members, escaped Unicode and signed i64 boundary values from raw wire bytes.
- Exercise all four client/provider version pairs and a tampered bundle that has the expected version label.

## Phase 1 — Specify and load the HTTP contract

Work graph task `w:httpVocabulary`. Create `docs/language/http-core.md`, `src/http/{mod.rs,model.rs}`, `scripts/setup-http-conformance.sh` and `examples/http/contract/v1/domain.ttl`. Extend `src/main.rs`, factor reusable verified byte loading from `src/contracts.rs`, and add `tests/http_model.rs`. The library entry point `http::load(project: &Path, lock: &Path, cache: &Path) -> Result<HttpContract, HttpError>` loads one published HTTP pin and its pinned ledger dependency. Separate the authoring entry point `http::load_source(root: &Path, dependency_lock: &Path, cache: &Path) -> Result<HttpContract, HttpError>` from published release resolution. The authoring lock pins dependencies only. The release pin is created after the manifest has been written. Define `Iri` as a validated named RDF identifier. The HTTP model needs operations, roles, field uses, constraints, named errors and dependencies by IRI. Each field has a stable IRI, a stable declared native name and an explicit wire name. An operation references a field through its request or response record. Include these properties in the first release so the rename can change only the wire name. Name the demo operation IRIs `urn:oddlang:ledger-http:LookupAccount` and `urn:oddlang:ledger-http:TransferFunds`. Keep ledger model validation separate. Factor ledger cache validation into `contracts::resolve_pin(&Pin, &Path) -> Result<Release, String>` and let the existing project resolver delegate to it after checking the project import.

- [x] Write the vocabulary table with exact IRIs, cardinalities, lexical rules, request ordering and error precedence. Give each profile rule a stable ID and list applicable roles and required witness kinds. Specify operation paths, percent decoding, and deterministic lookup and transfer state observations. Document pinned tooling and setup. Specify `pins[]` workspace and dependency lock entries as `{identity, version, manifestSha256}`. Project imports select workspace entries by identity or exact version IRI. The source lock covers external dependencies including the v1 ledger. Use `CACHE/ledger/VERSION` for the legacy identity and `CACHE/http/<hex SHA-256 of the UTF-8 identity>/VERSION` for HTTP releases. Require HTTP manifest `schemaVersion`, `identity`, `version`, `entry`, `ruleSetVersion`, `dependencies[]` (exact pins) and `files` (relative path to SHA-256). Reject non-normal paths and symlink escapes. Preserve existing local import set semantics and declare whether each referenced import is local or a pinned dependency. Pin a JSON Schema 2020-12 validator and the OpenAPI 3.1 schema in setup. In phase 1 use a hand-authored minimal published fixture.
- [x] Write `http_model` tests for a good fixture, missing or unknown normative properties, duplicate method/path, unresolved IRI, a cyclic local import that resolves once per file, conflicting dependency pins, one byte changed in a pinned file, and reordered Turtle with renamed blank nodes. Run `cargo test --locked --offline --test http_model` and confirm missing entry point failures.
- [x] Implement the loader and `oddlang http check-source SOURCE DEPENDENCY_LOCK CACHE` and `oddlang http check PROJECT WORKSPACE_LOCK CACHE` for the two entry points. Resolve dependencies inside the offline cache from explicitly pinned manifest digests, verify bytes before parse, and keep errors ordered by semantic IRI and predicate path.
- [x] Rerun `http_model` and `contract_release`. Pass when the expected model loads, all negative inputs fail and legacy releases resolve unchanged. Commit and record the Claude review and verification.

## Phase 2 — Publish portable obligations, cases and schemas

Work graph task `w:httpBundle`. Create `src/http/{obligations.rs,bundle.rs,schema.rs}`, `docs/language/conformance-bundle.md` and `tests/http_bundle.rs`. Public entry points are `inventory(&HttpContract) -> Vec<Obligation>` and `publish(&HttpContract, &Path) -> Result<(), HttpError>`. Publish the verified source closure and dependency pins alongside `manifest.json`, `obligations.json`, `cases.json`, `schema.json`, `openapi.json` with relative payload paths. Include compatibility only for releases with a named predecessor, starting in Phase 5. Define `Obligation` as a declaration IRI, role, rule ID and ordered witness slots (use position and kind). Store entries and their case IDs in `obligations.json`. Put `ruleSetVersion: 1` in the manifest and add it and the manifest digest to evidence keys after verifying the bundle. Keep evidence outside the release manifest to avoid a self-reference.

- [x] Specify raw request/response envelopes, ordered exchanges, fixture setup data, observations and normalized evidence. Encode raw body bytes as base64 so malformed UTF-8 survives JSON serialization. A local-rejection case expects no exchange. Store consumer claim manifests at `examples/http/clients/{typescript,go}/claim.json` and a provider claim beside the Rust example. A claim file contains schema version and a list of operation IRI/role pairs. Evidence contains schema version, exact release pin, rule-set version, case results (`caseId`, `outcome`, `observations`) and claim pairs. Resolve a claim to required obligations using the contract graph, and define `select_cases(&VerifiedBundle, &Claim) -> Result<Vec<CaseId>, HttpError>` to expand those obligations to case IDs. Expose `verify_evidence(&VerifiedBundle, &Claim, &Evidence) -> Result<(), HttpError>` and `oddlang http verify-evidence BUNDLE PIN CLAIM EVIDENCE` for CI. Compute outcomes by comparing native observations to the independent expected outcomes in the bundle. Report missing cases as unexecuted. A runner-supplied pass flag cannot override mismatched observations. Assert that missing, mismatched and duplicate observations fail even when a runner reports success. Validate case associations against their declared role and witness kind. Reject unknown claims, duplicate case IDs and stale, missing or failed evidence. Give each case stable IDs, obligation references, witness kind, expected response or native outcome and expected post-state where applicable. Use explicit distinctions between wrong wire shape, named operation error and peer/protocol failure.
- [x] Write independent fixtures asserting `GET` with balance `"9223372036854775807"` succeeds and `"9223372036854775808"` as transfer amount is a 400. Pin a hand-authored expected inventory and assert deleting a required positive or negative witness blocks publication. Store authored scenarios in `examples/http/contract/v1/scenarios.json`, listed by the HTTP entry point and pinned as a source payload in the manifest. Use the portable scenario format with authored IDs and witness-slot references. Validate references at publication and merge the authored cases with rule-derived cases in case ID order. Hand-author transfer scenario expectations, including A=10, B=7 and amount=3 → A=7, B=10. Cover all six ledger guard errors, the first error when adjacent guards can both fail, the exact destination capacity and the first overflowing amount. Cross-check published outcomes against the existing independent test oracle in `http_bundle`. Add lookup missing and successful maximum-balance scenarios. Assert case order and derived payload bytes survive an isomorphic graph rewrite.
- [x] Run `cargo test --locked --offline --test http_bundle` and confirm the missing publisher fails. Implement deterministic rule derivation, scenario validation, manifest packaging and local-reference schema generation. Expose `cases(&HttpContract) -> Result<Vec<Case>, HttpError>` and `gaps(&[Obligation], &[Case]) -> Vec<WitnessGap>`, and exercise the same release gate after removing a case from the derived inventory. Add `oddlang http publish SOURCE DEPENDENCY_LOCK CACHE OUTPUT`. Write the exact source closure and dependency pins into the release, then emit its manifest and a separate workspace pin. Save the v1 fixture under its prescribed cache path and pin its manifest digest. Isomorphic-source tests compare derived payloads, while two builds from identical source compare every file. Test publication into an empty output directory and resolve the resulting release with that pin. Validate the OpenAPI and JSON Schema artifacts with pinned validators and compare representative accept/reject cases to the portable corpus, with decimal range as the documented extension.
- [x] Rerun `http_bundle` and verify two fresh output directories are byte-identical. Commit and record the Claude review and verification.

## Phase 3 — Prove a real Rust provider

Work graph task `w:httpProvider`. Create `src/http/rust.rs`, `examples/http/provider/` and `tests/http_provider.rs`. The projection entry point is `emit_rust(&HttpContract, &Path) -> Result<(), HttpError>`. Generate checked Rust DTOs and binding code for Axum. The demo implements a generated service interface with the existing v1 ledger operation and an isolated in-memory fixture store. Add `oddlang http generate PROJECT WORKSPACE_LOCK CACHE OVERLAY OUTPUT`. Author an initial `examples/http/provider/overlay.json` and define `load_overlay(&Path) -> Result<TargetOverlay, HttpError>` in `src/http/overlay.rs`. Overlay v1 contains `schemaVersion`, `bindings[]` with `role`, `target` and binding ID such as `axum`, and optional advisory `hints[]` scoped to the same pair. Required bindings select only the requested output. Test missing or unknown required bindings, plus distinct hints yielding identical contract digests.

- [x] Write a provider harness to build the locked example, launch a fresh process on loopback per scenario with `--fixture FILE --listen 127.0.0.1:0`, await its `listening HOST:PORT` line with a timeout and run ordered raw HTTP exchanges. Assert 415 for unsupported media type, 400 for duplicate keys and raw JSON numeric amount, and exact ledger error IRIs. Use subsequent account GETs on success and failure, including an unrelated account. Require every claimed obligation to have evidence.
- [x] Run `cargo test --locked --offline --test http_provider` and confirm the absent binding fails. Implement parsing, native types and the generated binding. Decode the original body at the boundary before framework JSON helpers can discard duplicate keys.
- [x] Run the provider test with the stock ledger implementation and separate test-only variants that write on error, swap guard order, and allow a noncanonical amount. Each variant must fail its expected portable cases. Require complete passing evidence for the stock provider. Commit and record the Claude review and verification.

## Phase 4 — Generate a TypeScript client and prove independent adoption

Work graph task `w:httpConsumers`. Create `src/http/typescript.rs`, `examples/http/clients/typescript/`, `examples/http/clients/go/` and `tests/http_consumers.rs`. The TS projection entry point is `emit_typescript(&HttpContract, &Path) -> Result<(), HttpError>`. Add `examples/http/clients/typescript/overlay.json` selecting the `fetch` binding. The generated interface takes a base URL and injected Fetch-compatible function and returns a checked result or a distinct protocol failure. The standalone Go module consumes a bundle directory (`manifest.json` and its listed files), a release pin and its claim. Its own `go test` harness creates the scripted peer. Verify manifest and payload bytes against the pin before using cases. Both publish the same machine-readable evidence. Use the case and observation protocol defined in Phase 2 to implement scripted peers in Node and Go. For each case the native runner starts a fresh loopback server with the scripted reply, invokes the client against its assigned URL, checks the captured exchange and native outcome, then writes a case result. Use a versioned result vocabulary for checked values, declared errors and protocol failures. Compare their evidence via the Phase 2 verifier.

- [ ] Write a scripted-peer harness that asserts actual method, path, headers and body, and serves valid success, declared errors and malformed responses. Compare the decoded path, including an ID containing space, slash and non-ASCII characters. Reject empty and dot-segment IDs locally. Exercise invalid UTF-8, an unpaired surrogate and duplicate decoded names from raw fixtures. Check amount `9007199254740993n` encodes as the same decimal string. Assert consumers reject duplicate members, unknown error IRIs, mismatched error status, malformed JSON and out-of-range balances. Assert known error IRIs return checked native errors.
- [ ] Run `cargo test --locked --offline --test http_consumers` and confirm missing clients fail. Implement shared TS codec/client with no Node-only imports, using bigint for exact values, and Go with only native tooling. Use byte-level validation and a strict, duplicate-aware parser before object construction. Read TS replies as bytes and use fatal UTF-8 decoding. For Go, check UTF-8 and validate keys and escapes without case-insensitive struct decoding. Test a same-version altered bundle with both clients. Run all cases selected for each claim against the peer and run a real-provider smoke test.
- [ ] Mutate the encoder and decoder independently in each client using test-only copies. Confirm the shared verifier identifies the exact targeted cases for each mutation and untouched cases still pass. Verify the Go command works with only the bundle and Go fixture copied outside the Oddlang checkout. Commit and record the Claude review and verification.

## Phase 5 — Expand the JSON profile and verify pin changes

Work graph task `w:httpEvolution`. Deliver the wire evolution check first, then extend the model, rules and projections from phases 1–4 as a separately reviewed codec task. Add the richer type fixtures at `examples/http/contract/shapes/v1/domain.ttl` under their own contract identity. Add `examples/http/contract/v2/domain.ttl` and `tests/http_evolution.rs`. Export `compatibility(old: &HttpContract, new: &HttpContract) -> CompatibilityReport` and `affected(contract: &HttpContract, changed: &[Iri]) -> Vec<Obligation>` from `src/http`. Define `CompatibilityReport` as two directional verdicts and a sorted list of changes with declaration IRI, kind and before/after values. For shape changes beyond the implemented compatibility rules, return an unknown verdict and fail automatic promotion.

- [ ] Write `http_evolution` tests for the two compatible same-version pairs and two incompatible mixed pairs. Keep the demo v2 vocabulary unchanged and vary only the required balance wire name. Assert the exact field IRI appears in the diff, a re-pinned test change to a named HTTP balance constraint selects affected reader and writer cases transitively, and an unrelated change selects neither. Use existing `GET /accounts/{id}` with a successful response to distinguish version pairs. The off-diagonal checks must fail at response decoding because each peer omits the expected required member. Exercise a mixed transfer and use an independent GET to show that the committed state changed even though the client failed to decode. Run and confirm the missing or wrong verdict fails.
- [ ] Implement the IRI-based diff and impact traversal. Keep native field names derived from a stable declared name associated with the field IRI. Restrict the wire rename to codecs. - [ ] Add and review a separate codec change. Write portable cases for nested records, lists, optional versus nullable fields and closed tagged unions in `tests/http_shapes.rs`. ## Phase 6 — Exercise Node SSR and React together

Work graph task `w:httpHybrid`. Create `examples/http/hybrid/{ssr,web}/`, `scripts/verify-http-conformance.sh` and `tests/http_hybrid.rs`. Pin React, a Vite build and Playwright at exact versions in `examples/http/hybrid/package-lock.json` and install the browser selected by the pinned Playwright package in the setup step. Use one workspace lock and one generated client package for both app entries. Deploy Rust behind the same local origin for browser requests and address it through a configured service URL for SSR. Keep application rendering and the proxy native.

- [ ] Add a Node SSR assertion that the initial HTML contains an account balance from the real Rust service. Add a headless browser test that loads the React view, posts a transfer and renders both updated balances, then shows InsufficientFunds when A=10 and B=7 are seeded, a transfer of 3 succeeds, and a second transfer of 8 from A fails. Assert the Rust account lookup confirms preserved state after that error. Confirm the tests fail before frontends are wired.
- [ ] Build the two apps, update only the workspace pin and regenerate both against v2. Run the same display and transfer checks, capture a v2 response and assert `balanceMinor` on the wire. Keep the prior v1 provider under `target/http/v1` and the rebuilt v2 provider and clients under `target/http/v2`. Run the independently pinned Go v1 client against the parallel v1 endpoint.
- [ ] Wire the offline script to verify regenerated artifacts, provider and consumer evidence completeness, the four version pairs, the Go standalone fixture, and both app tests. Document setup, runtime versions, role claims, evidence paths and unsupported profile features. Run the offline script plus the existing ledger suite with its pinned PostgreSQL configuration. Commit and record the Claude review and verification.

The release is ready when a fresh clone with the pinned tools cached can publish, build and verify these artifacts offline. A deliberately faulty implementation must fail the same portable suite even when another native target succeeds.
